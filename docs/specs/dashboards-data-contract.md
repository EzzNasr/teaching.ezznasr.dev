# teaching.ezznasr.dev — Student & Master Dashboards: Master Plan (v1)

For how the system works generally, see `PROJECT_REFERENCE.md`. For what
was actually built, deployed, tested, and what's still open across every
session, see `PROJECT_HISTORY.md` — this document is the stable technical
spec/data contract and stays that way; current build/deploy status is
tracked there, not duplicated here. See the addendum at the end of this
file for one real schema extension made after this v1 spec was written.

Dashboards are hand-authored static pages (not generated by `app_main.py`,
same as the homepage) — this doc covers everything *behind* them: the data
model, the auth changes, and the exact request/response shape each new
`Code.gs` action returns, so the dashboard pages have a fixed contract to
build against.

## 1. Data model — two new Sheets, Drive JSON stays as-is (locked)

**Why a Sheet at all:** every quiz result and submission is currently its
own JSON file in a Drive folder. A dashboard that wants "everything for
student X" or "everything, period" would have to open every file
individually — each is a separate Apps Script API call, and that hits real
walls fast (execution time cap, per-call quota) as the file count grows.
Reading N rows out of a Sheet is *one* call regardless of N.

**Why not folder-per-student instead:** that idea (grouping
`submissions/<student>/...`) genuinely speeds up "one student's own
history" — you only open one folder. But it does nothing for "everyone,
all at once," which is what the master dashboard needs: you'd still open
every student's folder and read every file inside, same total work as one
flat folder. The bottleneck is the number of individual file reads, not
how they're organized into folders. So: Sheet for the index/aggregation
layer, Drive JSON unchanged as the durable per-attempt record. Folder
organization in Drive is still worth doing for your own manual browsing if
you want it — it just isn't what makes the dashboards fast.

### `QuizResults` sheet
One row per quiz attempt, written by `handleUploadQuizResult` in addition
to (not instead of) today's Drive JSON file.

| column | notes |
|---|---|
| `student_id` | phone digits, as today |
| `name` | display name at time of attempt |
| `subject` | |
| `lesson` | |
| `quiz_title` | |
| `date` | |
| `start_time` / `end_time` | |
| `score` / `total` | |
| `questions_json` | the full per-question array (`question`, `your_answer`, `correct_answer`, `is_correct`, `chapter`) as a JSON string in one cell |

### `Submissions` sheet
One row per assignment submission, written by `handleUploadSubmission`
alongside the existing Drive file/meta.

| column | notes |
|---|---|
| `student_id` | |
| `name` | |
| `subject` / `lesson` | |
| `submission_type` | text / url / file |
| `text` | full text inline **up to ~49,000 characters** — right against a Sheets cell's ~50,000-character hard cap, leaving just enough headroom to be safe. Master dashboard reads it straight from here, no Drive open needed for the common case. |
| `text_truncated` | boolean — true if the cell holds a preview only |
| `url` / `note` | |
| `file_id` / `file_name` | for file submissions — dashboard links out to Drive for the actual file, same as today |
| `date` / `submitted_time` | |

Oversized text (rare) stores a preview + `text_truncated: true`; the full
text still lives in the Drive JSON exactly like it does today — nothing
about full-fidelity storage changes.

## 2. Auth changes (locked)

### Session token — closes a real hole, doesn't change multi-device login

Today `student_id` is just the phone number's digits — not a secret.
Nothing stops a request claiming to be `student_id: 01xxxxxxxxx` from
reading that student's data once a "give me my results" action exists.
Fix:

- `register_student` generates one random `session_token` (`Utilities.getUuid()`), stored as a new column on that student's `Students` row.
- `login_student` returns that same stored token every time (not a new one per login).
- The browser caches it in `localStorage` next to `student_id`/`student_name`, same place as today.
- Any data-fetching action requires the token and checks it against the row for that `student_id` before returning anything.

**This does not lock a student to one browser/device.** Logging in on a
second device is the same phone+password flow as today, and that login
returns the *same* token to the new device too — both stay valid
simultaneously. What it actually prevents is someone who merely *knows* a
phone number (no password) pulling that student's data. Revocation, if
you ever need it, is the same as today: delete/reset that student's row.

### Admin access — no shared secret, your own login instead

Reusing `ADMIN_TOKEN` (the string already gating attachment uploads) for
the dashboard was the original idea, and it's genuinely worse here than it
is for its current job. It's a static string checked with plain equality —
whoever holds it has full access, indefinitely, from anywhere, with no way
to tell who's using it or revoke just one holder. That's an acceptable
risk for "gates a button in a desktop app only you run"; it's a bad fit
for "grants read access to every student's grades from a web page" (leaks
through screenshots, shared machines, config files, no attribution if it
ever needs to be shared).

**Decided instead:** you log into the dashboard the exact same way
students log in — phone + password, same `auth.js` flow, same
`login_student` action. One new column on your own row in `Students`:
`is_admin = TRUE`, set by hand directly in the Sheet, once. No web-facing
action ever writes this column, so nothing exposed to the internet can
grant it. Admin-only actions check: does this request's `session_token`
belong to a row where `is_admin` is true? If yes, serve everything; if no,
reject. Revocable the same way a student account is (edit the cell).
`ADMIN_TOKEN` itself is untouched — still exactly what gates
`upload_attachment`/`delete_attachment` from the desktop app, unrelated to
any of this.

## 3. New `Code.gs` actions

Aggregation (by chapter, by lesson, "most missed," trends over time) all
happens **client-side, in the dashboard's own JS**, after one bulk fetch —
not as separate server-side actions per view. `Code.gs`'s job stays
simple: authenticate, then hand back the full rows. The browser already
has the per-question JSON in each row once it's loaded, so slicing it by
chapter/lesson/wrong-answer-count is cheap in-memory work, and it avoids
needing a new endpoint every time you think of a new way to filter the
data. Full data in the browser is fine at the scale a single teacher's
class operates at — worth revisiting only if the roster grows large
enough that the bulk payload itself gets unwieldy.

### `get_my_results`
Request: `{ action: "get_my_results", student_id, session_token }`
Auth: token must match the row for that `student_id`.
Response:
```json
{
  "ok": true,
  "quiz_results": [ /* that student's QuizResults rows */ ],
  "submissions": [ /* that student's Submissions rows */ ]
}
```

### `admin_get_all`
Request: `{ action: "admin_get_all", student_id, session_token }`
Auth: token must match a row where `is_admin` is true.
Response:
```json
{
  "ok": true,
  "students": [ /* roster: phone, display_name, created_at — no password hashes */ ],
  "quiz_results": [ /* every row, every student */ ],
  "submissions": [ /* every row, every student */ ]
}
```

This one response is everything the master dashboard needs — filtering by
subject/lesson/chapter/student/date, "most wrong questions" ranking,
per-chapter accuracy, assignment completion status, full submission text —
all derived from these three arrays in the page's own JS.

## 4. What each dashboard is responsible for

Both are hand-built static pages, gated by the existing `auth.js`
`mount()` flow (unchanged) — the only difference between them is which
account logs in and which action it calls after.

- **Student dashboard** — logs in as the student, calls `get_my_results`,
  shows that student's own quiz history and submissions. Chapter-level
  breakdown for their own attempts is easy to add here since the data's
  already flowing.
- **Master dashboard** — logs in as you (`is_admin` row), calls
  `admin_get_all`, gets the full dataset described above. Everything
  beyond that — the actual filter/sort/aggregate UI — is on your side to
  build, this doc just fixes the shape of what it receives.

## 5. Rollout order

1. Add `session_token` + `is_admin` columns to `Students`; set `is_admin`
   on your own row by hand.
2. Add `QuizResults` + `Submissions` sheets.
3. Update `register_student`/`login_student` to issue/return the token.
4. Update `handleUploadQuizResult`/`handleUploadSubmission` to also write
   the Sheet row (Drive JSON untouched).
5. Add `get_my_results` and `admin_get_all`.
6. You build the two dashboard pages against the response shapes above.

Nothing here requires touching already-live quiz/assignment pages or
breaking existing data — steps 1–5 are additive to `Code.gs`, same
rollout-safety posture as the original login work (ship additive changes,
verify, only then anything stricter).

## 6. Decisions confirmed

1. Column/sheet names in this doc are final as written.
2. Text-inline threshold is ~49,000 characters (the max that safely fits
   a Sheets cell) — Submissions almost never fall back to a truncated
   preview.
3. "Most missed questions" ranking keys on exact question text + lesson,
   not question text alone, so identical wording in two different lessons
   is never accidentally merged.
4. Session tokens are persistent — they last until you manually clear
   that student's row, no auto-expiry, no rotation on logout.

### Step 1 — Sheet helpers (`Code.gs`)

No manual Sheet setup needed — this is fully automatic, same pattern as
the existing `_students()` header-row bootstrap. Add:

```js
function _ss() {
  var id = _props().getProperty("STUDENTS_SHEET_ID");
  if (!id) throw new Error("STUDENTS_SHEET_ID isn't set in Script Properties.");
  return SpreadsheetApp.openById(id);
}

// Creates the tab (with header row) on first use if it doesn't exist yet.
function _sheetByName(name, headers) {
  var ss = _ss();
  var sheet = ss.getSheetByName(name);
  if (!sheet) sheet = ss.insertSheet(name);
  if (sheet.getLastRow() === 0) sheet.appendRow(headers);
  return sheet;
}

function _quizResultsSheet() {
  return _sheetByName("QuizResults", [
    "student_id", "name", "subject", "lesson", "quiz_title",
    "date", "start_time", "end_time", "score", "total", "questions_json",
  ]);
}

function _submissionsSheet() {
  return _sheetByName("Submissions", [
    "student_id", "name", "subject", "lesson", "submission_type",
    "text", "text_truncated", "url", "note", "file_id", "file_name",
    "date", "submitted_time",
  ]);
}

// Shared by both dashboard-facing actions: turns a sheet's rows into
// [{header: value}, ...] using row 1 as keys.
function _sheetValuesAsObjects(sheet) {
  var values = sheet.getDataRange().getValues();
  if (values.length < 2) return [];
  var headers = values[0];
  return values.slice(1).map(function (row) {
    var obj = {};
    headers.forEach(function (h, i) { obj[h] = row[i]; });
    return obj;
  });
}
```

### Step 2 — `Students` sheet gains `session_token` + `is_admin`

Replace `_students()` and `_findStudentRow()`. This deliberately keeps
using `ss.getSheets()[0]` (the *first* tab, whatever it's named) rather
than looking it up by name — your existing registered rows live in
whatever tab that already is, and switching to a name-based lookup would
silently create a second, empty tab instead of finding them.

```js
function _students() {
  var sheet = _ss().getSheets()[0];
  if (sheet.getLastRow() === 0) {
    sheet.appendRow(["phone", "password_hash", "display_name", "created_at", "session_token", "is_admin"]);
  } else {
    _ensureStudentColumns(sheet);
  }
  sheet.getRange(1, 1, Math.max(sheet.getMaxRows(), 2), 1).setNumberFormat("@");
  return sheet;
}

// Adds the two new headers to an existing sheet that predates this
// change, without touching any already-registered rows.
function _ensureStudentColumns(sheet) {
  var headers = sheet.getRange(1, 1, 1, sheet.getLastColumn()).getValues()[0];
  ["session_token", "is_admin"].forEach(function (col) {
    if (headers.indexOf(col) === -1) {
      sheet.getRange(1, sheet.getLastColumn() + 1).setValue(col);
    }
  });
}

function _findStudentRow(sheet, phone) {
  var target = _normalizePhone(phone);
  if (!target) return null;
  var values = sheet.getDataRange().getValues();
  for (var i = 1; i < values.length; i++) {
    if (_normalizePhone(values[i][0]) === target) {
      return {
        row: i + 1,
        phone: values[i][0],
        password_hash: values[i][1],
        display_name: values[i][2],
        created_at: values[i][3],
        session_token: values[i][4] || null,
        is_admin: values[i][5] === true || String(values[i][5]).toUpperCase() === "TRUE",
      };
    }
  }
  return null;
}
```

Mark yourself as admin **once, by hand**: open the Students tab, find your
own row, put `TRUE` in the `is_admin` column. Nothing else ever writes
that column.

### Step 3 — issue/return the session token

Replace `handleRegisterStudent` and `handleLoginStudent`:

```js
function handleRegisterStudent(payload) {
  if (!payload.phone || !payload.password_hash) throw new Error("Missing phone or password.");
  var sheet = _students();
  var existing = _findStudentRow(sheet, payload.phone);
  if (existing) throw new Error("An account with that phone number already exists — log in instead.");
  var phone = String(payload.phone).trim();
  var displayName = String(payload.display_name || phone).trim();
  var createdAt = Utilities.formatDate(new Date(), "Africa/Cairo", "yyyy-MM-dd HH:mm:ss");
  var token = Utilities.getUuid();
  sheet.appendRow([phone, payload.password_hash, displayName, createdAt, token, ""]);
  return { ok: true, student_id: _normalizePhone(phone), student_name: displayName, session_token: token };
}

function handleLoginStudent(payload) {
  if (!payload.phone || !payload.password_hash) throw new Error("Missing phone or password.");
  var sheet = _students();
  var found = _findStudentRow(sheet, payload.phone);
  if (!found) throw new Error("No account found for that phone number — register first.");
  if (String(found.password_hash) !== String(payload.password_hash)) {
    throw new Error("Incorrect password.");
  }
  // Accounts registered before this change won't have a token yet —
  // issue one on next login instead of forcing a re-registration.
  var token = found.session_token;
  if (!token) {
    token = Utilities.getUuid();
    sheet.getRange(found.row, 5).setValue(token);
  }
  return { ok: true, student_id: _normalizePhone(found.phone), student_name: found.display_name, session_token: token };
}
```

Add the two auth-check helpers used by the dashboard actions:

```js
function _requireStudentSession(payload) {
  if (!payload.student_id || !payload.session_token) throw new Error("Missing session.");
  var values = _students().getDataRange().getValues();
  var target = _normalizePhone(payload.student_id);
  for (var i = 1; i < values.length; i++) {
    if (_normalizePhone(values[i][0]) === target) {
      if (String(values[i][4]) === String(payload.session_token)) return true;
      throw new Error("Session expired or invalid — please log in again.");
    }
  }
  throw new Error("No matching student.");
}

function _requireAdminSession(payload) {
  if (!payload.student_id || !payload.session_token) throw new Error("Missing session.");
  var values = _students().getDataRange().getValues();
  var target = _normalizePhone(payload.student_id);
  for (var i = 1; i < values.length; i++) {
    if (_normalizePhone(values[i][0]) === target) {
      var isAdmin = values[i][5] === true || String(values[i][5]).toUpperCase() === "TRUE";
      if (String(values[i][4]) === String(payload.session_token) && isAdmin) return true;
      throw new Error("Not authorized.");
    }
  }
  throw new Error("Not authorized.");
}
```

### Step 5 — the two dashboard-facing actions

```js
function handleGetMyResults(payload) {
  _requireStudentSession(payload);
  var target = _normalizePhone(payload.student_id);

  var quizRows = _sheetValuesAsObjects(_quizResultsSheet())
    .filter(function (r) { return _normalizePhone(r.student_id) === target; });
  var subRows = _sheetValuesAsObjects(_submissionsSheet())
    .filter(function (r) { return _normalizePhone(r.student_id) === target; });

  return { ok: true, quiz_results: quizRows, submissions: subRows };
}

function handleAdminGetAll(payload) {
  _requireAdminSession(payload);

  var studentRows = _sheetValuesAsObjects(_students()).map(function (r) {
    return { phone: r.phone, display_name: r.display_name, created_at: r.created_at };
  });

  return {
    ok: true,
    students: studentRows,
    quiz_results: _sheetValuesAsObjects(_quizResultsSheet()),
    submissions: _sheetValuesAsObjects(_submissionsSheet()),
  };
}
```

Wire both into `doPost`'s switch statement, alongside the existing cases:

```js
      case "get_my_results":
        return _json(handleGetMyResults(payload));

      case "admin_get_all":
        return _json(handleAdminGetAll(payload));
```

### Step 6 — carry the token in `auth.js`

Wherever your current `auth.js` calls `saveSession({ student_id: data.student_id, student_name: data.student_name })` after a successful `login_student`/`register_student` call (there may be more than one call site if you've since added the corner-widget modal), add the token to that same object:

```js
saveSession({ student_id: data.student_id, student_name: data.student_name, session_token: data.session_token });
```

Nothing else about the session object changes — `AuthEngine.getSession()` will just include `session_token` from then on, which is what the dashboard pages send back on `get_my_results`/`admin_get_all` calls.

## Addendum — schema/action extensions since v1 (per `PROJECT_HISTORY.md` Phase 2–3)

This v1 spec did not originally include year tracking; it was added in a
later phase and is recorded here at the schema/contract level so this
document stays a complete, current reference. Full narrative (design
decisions, bugs found/fixed, what's still unverified) lives in
`PROJECT_HISTORY.md` §2–3 — this section only states the resulting shape.

- **`Students` sheet** gains a `year` column, values `"Senior 1"` /
  `"Senior 2"` / blank (blank = pre-existing account or not yet asked).
  Same additive-migration pattern as `session_token`/`is_admin` —
  `_ensureStudentColumns` back-fills the header on old sheets, existing
  rows are untouched.
- **`register_student`** accepts an optional `year` and echoes it back in
  the response. **`login_student`** also returns `year` (this was
  initially missed and fixed — see `PROJECT_HISTORY.md` §3.2 — since
  without it the client has no way to know a returning student is
  missing one).
- **New action, `set_year`** — session-authenticated (requires a valid
  `session_token`, not just a phone number), validates the value is
  exactly `"Senior 1"` or `"Senior 2"`. Lets a client backfill a missing
  year on an already-logged-in session without a fresh login.
- **`admin_get_all`**'s roster projection includes `year` per student.
- **Year applies to Programming lessons only** — English/Math are
  year-agnostic by explicit instruction; a Programming lesson's year is
  inferred from its live folder path (a `grade-N-secondary` segment),
  not stored per-lesson anywhere in `Code.gs`. This inference logic lives
  entirely in `master.html`'s own client-side code (reading GitHub's
  public tree API), not in `Code.gs` — nothing above needed for it to
  work is part of the `Code.gs`/`auth.js` contract itself.

As with the rest of this document: this describes the intended/recorded
shape, not a freshly re-verified read of live source in producing this
consolidated set — see `PROJECT_HISTORY.md` §4 for exactly which pieces
of this are confirmed live versus still pending deploy/test.

## Follow-up v2 additions (2026-11)

Source of truth: `Docs/02-plans/done/followup-v2/parallel-build-guide-followup-v2.md (outside the repo)`, section 3 (the frozen
contract). This is a summary for readers of this file. All times are computed in the `Africa/Cairo` zone and
**written for people as "Alex"** (`TZ_LABEL = "Alex"`). Stored values stay 24-hour (`"HH:MM"`, ISO with offset);
anything a person reads is 12-hour (`4:00 PM`, `4:00 م`).

### Names
- Event keys: `setup_missing`, `remind_watch`, `parents_watch`, `remind_hw`, `parents_hw`, `attendance`,
  `advance_lessons`. Hero phase = one event key or `all_clear`. Priority (top first): `attendance`,
  `parents_watch`, `parents_hw`, `remind_watch`, `remind_hw`, `advance_lessons`, `setup_missing`.
- Requirement keys: `watch`, `homework`, `quiz`, `attendance`, `written_answers`, plus `custom_<slug>` (manual).
- New sheets: `FollowupNotifications`, `FollowupDone`, `NotifySettings` (notifications); `Requirements`,
  `GroupRequirements`, `RequirementChecks` (requirements).

### Event engine (`assets/followup-events.js`, also generated into `FollowupLogic.gs`)
`FollowupEvents.eventsFor(overview, groupKey, nowIso)` →
`{group_key, tz_label, prev_session:{date,at_iso}|null, next_session:{date,at_iso}|null, phase, next_event_at_iso, events:[{key, state:"upcoming"|"due"|"expired"|"done", fire_at_iso, expires_at_iso, session_date, count, student_keys[], blocked_count, lesson}]}`.
`FollowupEvents.dueNow(overview, nowIso)` → `[{group_key, group, key, session_date, count, student_keys, lesson, blocked_count}]`.
The page and the hourly notifier both read it; the page never decides what is due by itself.

| Action | Request | Response |
|---|---|---|
| `admin_fu2_mark_done` | `{group:<group key>, kind:"watch"\|"hw"\|"advance", session_date}` | `{ok, done:[...]}` |
| `admin_fu2_notify_settings_get` | `{}` | `{ok, groups:{<group key>:{enabled,hour,snooze_until}}}` |

| `admin_fu2_notify_test` (admin only) | `{}` | `{ok, sent_to}` |
| `admin_req_get` / `admin_req_save_global` / `admin_req_save_group` / `admin_req_check` / `admin_req_history` | see guide 3.3 | see guide 3.3 |
| `admin_fu2_group_duplicates` (admin only) | `{}` | `{ok, duplicates:[{phone,name,groups}]}` |

The follow-up page sends the group **key** (lowercase, as in `groups[].key`) as `group` for the `admin_fu2_*`
actions, because the done / settings rows are keyed by it.

Page rules: `requirements.<key>.enabled === false` hides that requirement's chips, rows, buttons and steps;
`requirements.watch.rule.pct` replaces `settings.watch_done_pct` for that group.

### Monthly report
`admin_monthly_review` / `admin_student_summary` gain `summary.requirements = {items:[…], compliance_pct, source}`
(guide 3.6). Sent / closed months keep the snapshot they were sent with.

### Page deep links
`dashboard/followup.html#g=<group key>&step=<event key>` opens that group with that step in the hero card;
`#today` opens the Today tab. (`#student=<10 digits>` still works.)
